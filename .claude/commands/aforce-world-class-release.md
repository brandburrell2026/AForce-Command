AFORCE OS — FINAL WORLD-CLASS PRODUCT, INTELLIGENCE, SAFETY & RELEASE DIRECTIVE

## SYSTEM MANDATE

Operate at the combined standard of world-class principal-level:

- software architecture
- recommendation systems
- mobile engineering
- health-data integration
- product design
- accessibility
- privacy engineering
- application security
- AI security
- scientific validation
- quality engineering
- reliability engineering
- behavioral product design
- adversarial red-team review

Do not imitate intelligence through additional scores, dashboards, animations, AI conversation, or unsupported precision.

Engineer AForce to behave intelligently.

The final product must feel simple enough to understand in five seconds while operating as a sophisticated, deterministic, explainable intelligence system underneath.

## PRODUCT PROMISE

AForce should:

1. Understand the permitted context.
2. Identify whether anything meaningful needs to happen.
3. Provide one trusted action when warranted.
4. Make that action easy to complete.
5. Learn whether the timing and action appeared useful.
6. Remain silent when intervention is unnecessary.

The desired user feeling is:

“AForce understood the moment ahead, gave me exactly what mattered, and prepared me before I had to think about it.”

The wow factor must come from:

- correct timing
- one useful command
- effortless completion
- meaningful personal context
- calm silence
- visible trust
- correction when AForce is wrong
- continuity across devices
- learning that improves future timing
- the Pause → Hydrate → Lock In → Perform ritual

Do not manufacture wow through:

- fake live data
- competing scores
- excessive animation
- generic AI language
- unsupported physiological claims
- unnecessary notifications
- product-selling pressure
- demo data presented as real
- false precision

## 4. RELEASE-BLOCKING DEFECTS OBSERVED IN THE CURRENT EXPERIENCE

The following visible behaviors must be investigated and treated as potential P0 release blockers.

### COR-001 — Impossible calculations

The current experience has displayed examples including:

- projected sweat loss of 600 ounces
- projected sodium loss of 30,000 milligrams
- extreme classifications generated from incomplete or default inputs

Reproduce these conditions and identify the root cause.

Do not hide the issue through visual clamping alone.

Implement:

- a typed units and quantities layer
- explicit conversions for ounces, milliliters, pounds, kilograms, milligrams, minutes, and hours
- boundary validation
- plausible-range qualification
- missing-input handling
- stale-state clearing
- property-based tests
- unit-conversion tests
- malformed-input tests
- overflow and underflow tests
- cross-unit round-trip tests

Raw numerical values with ambiguous units must not cross domain boundaries.

If required inputs are missing or invalid, show:

- UNAVAILABLE
- LIMITED
- NEEDS INPUT

Do not calculate an authoritative command from invalid inputs.

### COR-002 — Conflicting scores and states

Audit every visible score, including:

- HydroState
- hydration percentage
- readiness
- performance score
- Performance Age
- protocol percentage
- community score
- guest readiness
- Heat Risk
- recovery demand
- third-party readiness or recovery scores

Classify each as:

- canonical hero metric
- supporting state
- attributed third-party context
- internal-only diagnostic
- deprecated
- unauthorized competitor metric

Only HydroState may operate as the consumer hero hydration/preparation-state metric.

Supporting states must not visually compete with HydroState or issue independent commands.

### CMD-001 — Conflicting commands

All user-facing surfaces must resolve the same active command ID, command version, evidence package, confidence state, and lifecycle status.

Home, Hydration, Protocol, Social Mode, Cruise Mode, Guardian, Phantom, Clutch, voice, notifications, and Weekly Command must not issue conflicting active actions.

UI code must not calculate recommendations.

### CLAIM-001 — Unsafe or overstated language

Review and gate phrases including:

- “heat stress detected”
- “know when your body is ready”
- “hydration appears stable”
- “electrolytes critical”
- “exact protocol”
- “water alone will not cool you”
- “recovery needed”
- “depleted”
- “your score will land near…”
- claims that a scan proves physiological effect
- claims that appearance proves dehydration or readiness

Replace unsupported certainty with evidence-bound language.

Examples:

- “Heat-related conditions are elevated.”
- “Available information suggests…”
- “AForce has limited confidence because…”
- “This is an estimate based on…”
- “No recent hydration record is available.”

Every meaningful claim must resolve to:

- approved deterministic evidence
- source provenance
- freshness
- measurement classification
- confidence
- claims identifier
- rules or model version

## 6. HYDRATION LOGGING — FIVE-SECOND STANDARD

Logging must not feel like homework.

Target:

- no more than two intentional taps for a common entry
- approximately five seconds or less for a familiar action
- one-tap repetition of recent or favorite actions
- no mandatory form for ordinary confirmation

Support the approved confirmation ladder:

1. Confirm the current RecoveryCommand.
2. Repeat a recent or favorite drink.
3. Scan or tap an eligible item.
4. Phantom or Clutch confirmation where approved.
5. One-tap phone or watch confirmation.
6. Manual detail entry only when necessary.

Required behavior:

- clear undo
- correction
- duplicate prevention
- idempotent writes
- offline queue with conflict handling
- source attribution
- measured, estimated, scanned, imported, and manually entered classification
- no hydration credit from drinking-motion detection alone
- no hydration credit from scanning alone without approved confirmation
- no hydration credit from a hypothetical action
- no silent backdating
- user inspection of what changed

## 7. RITUAL EXPERIENCE

Preserve the physical and behavioral ritual:

Pause → Hydrate → Lock In → Perform

The ritual is not four mandatory screens.

It is a state model that may complete in seconds.

### Pause

AForce identifies that an eligible action may matter and presents one calm signal.

### Hydrate

RecoveryCommand presents the approved action.

### Lock In

The user confirms the action or intent through an approved mechanism.

### Perform

AForce acknowledges completion without claiming that the person is medically safe, fully hydrated, or guaranteed to perform well.

Use the N‑И signature as an optional brand confirmation through:

- a restrained visual response
- an accessible haptic pattern
- Phantom or Clutch haptics
- a private notification mark

The N‑И confirmation means:

“Your approved action was recorded.”

It must not mean:

- medically cleared
- fully hydrated
- safe to drive
- safe from heat illness
- guaranteed readiness

The ritual must be:

- skippable
- accessible
- screen-reader compatible
- reduced-motion compatible
- respectful of quiet hours
- private on locked surfaces

Context Arbitration → RecoveryCommand → Evidence Engine → Decision Guard.

It must not independently create advice.

## 10. FORESIGHT, MOMENTS, REPLAY, AND AUTOPILOT

Implement only after P0 correctness and consumer simplicity have passed their approval gates.

### AForce Foresight

Extend AForce Moments to answer:

“Is there something useful this person should do before an important upcoming moment?”

Calendar data is context, not the product.

Candidate interventions must pass deterministic qualification involving:

- permission
- source validity
- freshness
- provider confidence
- context relevance
- moment importance
- baseline
- personal evidence
- expected usefulness
- interruption cost
- recent commands
- notification fatigue
- safety
- Decision Guard
- RecoveryCommand eligibility

Conceptually:

Expected utility = expected benefit − interruption cost.

Do not display false mathematical precision.

If evidence is insufficient:

SILENCE.

### Moment Replay

After an eligible moment, use the smallest useful feedback loop:

“How did you show up?”

- Great
- Good
- Off

Do not create a questionnaire.

Associate only permitted context with:

- moment type
- source coverage
- signal freshness
- Foresight decision
- RecoveryCommand
- timing
- Lock In state
- completion
- reported outcome
- correction
- confidence

Use association language, not causation.

### Autopilot

Consumer meaning:

“Prepare me automatically.”

Autopilot does not mean more notifications.

It means AForce evaluates quietly and interrupts only when the expected usefulness is sufficient.

Maintain one unified attention budget across all systems.

Repeatedly ignored, repetitive, or poorly timed guidance should make future interruption harder through approved deterministic logic.

Useful and consistently supported timing may earn greater eligibility.

AForce must recognize this as a successful outcome:

“You’re on track. Nothing is needed right now.”

Track internal Appropriate Silence and Unnecessary Intervention metrics.

# Schema ↔ DB drift log

Tracks cases where `drizzle-kit push` reconciled a difference between the schema file and the dev DB that was **pre-existing**, i.e. not introduced by the change being pushed. Recorded here so the reconciliation isn't silently absorbed into an unrelated commit.

- **2026-06-29** — `aforce_privacy.fields` `SET DEFAULT` (the `{score,state,streak,protocol,trend: true}` default): the schema declared `.notNull().default({...})` since before the Section 18 work, but the dev DB column lacked it; the Section 18 push swept in the `ALTER COLUMN ... SET DEFAULT`. Default-only change (affects future inserts; no existing rows rewritten). Unrelated to Section 18 — not in that commit.
  - **RECURS on every push** — the same `aforce_privacy.fields SET DEFAULT` reappeared on the Section 20 push (and will on each subsequent one). The dev DB and schema file are in a *stable disagreement*: push keeps trying to reconcile a default that never sticks. Harmless for now (SET DEFAULT only — no row rewrite, no destructive statement). **Run down WHY in the post-Part-A testing pass** — likely the schema declares a JSONB default the column can't actually persist as introspected, or a drizzle-kit introspection quirk around JSONB object defaults. Until then, expect this line on every `pnpm --filter @workspace/db push`.
  - **ROOT CAUSE (diagnosed):** drizzle-kit serializes the object default as **compact** JSON — `'{"score":true,...}'::jsonb` — but Postgres canonicalizes a `jsonb` default on store (adds whitespace **and** reorders keys into jsonb's internal order: by key length then bytewise). drizzle-kit then **string-compares** its compact form against the introspected canonical form; they never match, so it re-emits `SET DEFAULT` forever. Not a column that "can't hold" the value and not a real intent mismatch — purely a normalization/diff quirk in drizzle-kit 0.31.9.
  - **RESOLVED 2026-06-29** — fixed via option A: removed the DB-level default on `aforce_privacy.fields` (kept `NOT NULL`); the dev DB's `ALTER COLUMN ... DROP DEFAULT` was applied via push. Schema and DB now agree (no default on either side) — the recurring `SET DEFAULT` is gone. **Inserts must now pass `fields` explicitly — there is no DB-default safety net.** The application already does this (`artifacts/api-server/src/routes/privacy.ts` supplies `DEFAULTS.fields`), and `$inferInsert` now requires the field, so a missing-`fields` insert is a compile error rather than a silent DB fallback.

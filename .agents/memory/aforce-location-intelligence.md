---
name: AForce Location Intelligence surfacing
description: How Location Intelligence's two home surfaces split responsibility, and the locale rule that bit a code review.
---

Location Intelligence surfaces on the home screen through TWO distinct banners, by design — keep them separate:

- **Ambient environmental insight** (altitude / UV / air quality / heat+humidity note) → its own flag-gated banner that self-hides when the feature flag is off (home stays byte-identical).
- **Travel advisory** → owned by the Smart Modes "travel" mode, rendered by the Smart Modes banner. Do **NOT** add a second travel banner or surface travel in the ambient banner — that double-surfaces travel.

**Localization is part of "done", not a follow-up.** The pure Smart Modes engine holds only English fallback copy; a code review REJECTED the task because the visible guidance/labels weren't translated. The fix pattern: the pure engine exposes stable i18n *keys*, and the banner resolves them with `t(key, { defaultValue })`. Travel reuses the shared Location Intelligence travel-advisory key so the copy lives in one place. Launch locales (en/es/fr/de/pt/it) must carry the keys; hidden locales fall back to English via `fallbackLng`.

**Score-Protection + no-fabrication:** the environmental hydration adder is target-side and advisory only (never touches score). It now surfaces on the Home daily target as a READ-ONLY display projection (HydrationStatusCard target number + caption), layered on the SERVER-AUTHORITATIVE target — it never mutates `userState.dailyTarget` / reducer / realApi / server. TWO hard gates, not one: (1) the feature flag, AND (2) the snapshot **source must be `'live'`**. `getLocationSnapshot()` falls back to deterministic MOCK inputs (Denver/Miami, `source:'mock'`) on permission/network/native failure; honoring a mock reading on a user-visible target FABRICATES the user's environment (a code review caught exactly this). Gate the adder behind `locationCanAdjustTarget(enabled, source)` — checking the flag alone is not enough.

**The Home target adder must include EVERY environmental driver the acceptance lists — heat, humidity, altitude, UV, AND air quality.** Two separate code reviews REJECTED the wiring because `calculateLocationDemandAdderOz` (the ONLY value the Home overlay reads via `context.environmentalAdderOz`) excluded first air quality, then heat/humidity. Both were rationalized away ("air is advisory only / Score-Protection"; "heat/humidity handled by the demand engine's own ramp") — but the demand engine is DORMANT/test-only and never reaches the Home display, and the adder is target-side and never touches score, so excluding them both broke the owner's criterion ("hotter/more humid/higher-altitude/worse-air conditions raise the recommended target by a sensible, capped amount") with no compensating Score-Protection benefit. Fix: fold all five into `calculateLocationDemandAdderOz` (altitude 3/7/11, UV 2/4/6, AQI sensitive/unhealthy/hazardous 1/2/3, heat warm/hot/extreme 2/5/8, humidity very_dry/humid/oppressive 1/1/2; mild/comfortable add 0), still clamped to `LOCATION_DEMAND_CAP_OZ=14`. **Why:** (1) Score-Protection guards the SCORE, not the advisory display-only target; don't invoke it to suppress an owner-requested target adjustment. (2) "Handled elsewhere by the demand engine" is NOT handled if that engine is dormant — every driver must live in the one adder the runtime path actually consumes.

**Travel claims must be live↔live or inert — the demo MOCK is for ambient context, NEVER for movement.** The offline fallback rotates cities by day-of-year, so diffing two mock readings (or a live reading against a persisted mock baseline) looks like a trip the user never took. Guard travel at THREE points, not one: the snapshot assembler returns inert travel when the current reading isn't live; the snapshot persists an anchor only when the current reading is live (so a mock anchor never becomes a future baseline); and the consumer re-asserts source==='live' as defense-in-depth. **Also: when you change what may legitimately be persisted as a baseline, RETIRE the old persisted state** — bump the storage-key namespace. A pre-fix anchor is indistinguishable from a valid one, so a key bump is the only safe way to drop stale synthetic baselines (cost: one missed comparison on first post-upgrade reading, which correctly yields no travel). **Why:** same principle as `locationCanAdjustTarget` for the target adder — anything user-visible derived from location must be live or inert; mock data must never reach a movement claim, including indirectly via persistence.

**On-device Open-Meteo fetch is an OWNER-CONFIRMED keep, not a migration backlog item (decided June 2026).** The server proxies OpenWeather purely to hide its API KEY (and stay under the 60/min free tier); Open-Meteo is KEYLESS, so that rationale doesn't apply. Routing it through the server would buy only architectural consistency + coord-bucketed cross-user caching at scale — judged not worth the medium effort at current scale. So both on-device consumers fetch Open-Meteo directly with a 10-min in-memory TTL: `locationIntelligenceService` (forecast + air-quality + elevation) and `cityClimateService` (temp/humidity/condition for the status strip). **Why / how to apply:** don't "fix" this divergence on sight — it's a deliberate decision. If a future scale/consistency need revives it, the migration touches BOTH services + the OpenAPI spec + codegen, and must preserve the no-fabrication gate (the `live`/`mock` decision keys off on-device GPS success, NOT the weather fetch, so weather can move server-side without reopening travel fabrication).

**Why:** the spec asked for an insight note AND a travel banner, but travel was already wired through Smart Modes — so the only genuinely new ambient surface is the insight note, and travel work goes through Smart Modes.
